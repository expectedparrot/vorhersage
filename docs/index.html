Vorhersage
German for “forecast.”

The workbench

A process an agent can resume.

The agent researches the world and supplies judgments. Vorhersage stores the state, supplies the next task, validates its inputs, performs declared calculations, and preserves the resulting forecast.

01

Define the event

Fix YES, NO, and void rules, a deadline, and a resolution source before interpreting the probability.

02

Trace the evidence

Keep sourced findings, copied reports, contradictions, and explicit unknowns attached to the reasoning.

03

Preserve the forecast

Freeze the estimate and its inputs. Record revisions as new forecasts, with links to their predecessors.

04

Learn from outcomes

Resolve the precise question, compare eligible forecasts, and inspect Brier scores and descriptive calibration.

A clear boundary. The CLI does not choose a model or web service. Agents and configured workers collect evidence and interpret it. A complete workflow establishes an audit trail; forecasting accuracy still needs evaluation.

Get started / Python 3.11+

Install, then choose how to follow along.

From a terminal, install the checkout in a virtual environment. The package has no additional runtime dependencies.

Terminal / install
git clone https://github.com/expectedparrot/vorhersage.git
cd vorhersage
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
vorhersage version

Walk through the commands

Start at step 1 to create your own temporary study and follow every input through evidence, review, revision, and scoring. All data is fictional.

Run the existing example

Run the factory portfolio below to see the full result first. It creates two questions, a baseline, an updated forecast, and a matched evaluation.

Terminal / existing factory example
forecast_demo=$(mktemp -d "${TMPDIR:-/tmp}/vorhersage-demo.XXXXXX")
python examples/factory/walkthrough.py "$forecast_demo"
vorhersage --project "$forecast_demo" report --question factory_east --format markdown
python -m json.tool "$forecast_demo/summary.json"

Expected: two resolved questions, a successful integrity check, and matched Brier losses of 0.07625 for the fixture agent and 0.25 for the 50% baseline. Every input and task response is saved in the output directory. No model calls or API keys are involved.

The numbered walkthrough creates a separate project, so you can run both paths. Keep commands in the same terminal; the later snippets reuse the shell variables introduced in step 1.

01 / Define the question

Start with an event we can resolve.

We will forecast a shipment from fictional factory East, following the factory portfolio example. You will issue 40%, revise it to 75% after a fictional update, then record a YES outcome and score the final forecast.

Run the numbered steps in order, in the same Bash or Zsh terminal with the virtual environment active. They use Python’s standard library to read JSON; no jq, model service, or API key is needed. The commands create a fresh temporary study and generate timestamps at runtime.

Prefer to run everything first? From the repository root, run bash docs/assets/factory-walkthrough.sh, or download these commands as a script. The numbered sections below explain the same commands.
Terminal / keep this shell open
forecast_project=$(mktemp -d "${TMPDIR:-/tmp}/vorhersage-guide.XXXXXX")
vf() { vorhersage --project "$forecast_project" "$@"; }
json_field() {
  python -c 'import json,sys; print(json.load(sys.stdin)["data"][sys.argv[1]])' "$1"
}
forecast_time() {
  python -c 'import sys; from datetime import datetime,timedelta,timezone; print((datetime.now(timezone.utc)+timedelta(days=float(sys.argv[1]))).isoformat())' "${1:-0}"
}
forecast_deadline=$(forecast_time 1)
forecast_review=$(forecast_time 0.5)
vf init --name "Factory tutorial"
printf 'Study directory: %s\n' "$forecast_project"

vf is a shell shorthand for vorhersage --project "$forecast_project". The two small helpers read returned identifiers and create timezone-aware timestamps. init creates the study’s SQLite store.

Terminal / register a precise event
vf question add --from - <<JSON
{
  "id": "factory_east",
  "text": "Will fictional factory East ship by tomorrow?",
  "yes": "A qualifying shipment is recorded by the deadline.",
  "no": "No qualifying shipment occurs by the deadline.",
  "void": "The fictional event is withdrawn.",
  "event_deadline": "$forecast_deadline",
  "resolve_after": "$forecast_deadline",
  "resolution_source": "urn:vorhersage:fictional:dispatch",
  "event_group": "factory_east",
  "domain": "operations",
  "profile": "general",
  "kind": "simulation"
}
JSON

Expected: data.question_id is factory_east and data.version is 1. The general profile requires research on base rates, current state, actors and process, and contrary evidence. These will become four separate tasks.

The simulation label describes this example honestly. For a real event, use kind: "real", a verifiable resolution source, and concrete YES/NO rules. New wording creates a new question version; it does not rewrite an issued forecast.

02 / Preserve the research

Attach a finding to its source.

In a real forecast, an agent gathers this information from sources or Epiq. Here we author a clearly fictional observation. research capture packages the source and finding, preserves their relationship, and returns an evidence reference.

Terminal / freeze the initial evidence
vf research capture --from - > "$forecast_project/packet.json" <<JSON
{
  "sources": [{
    "id": "initial",
    "url": "urn:vorhersage:fictional:initial",
    "title": "Fictional factory status",
    "excerpt": "Preparation is underway; dispatch remains uncertain.",
    "retrieved_at": "$(forecast_time)"
  }],
  "findings": [{
    "id": "readiness",
    "claim": "Preparation is underway; dispatch remains uncertain.",
    "claim_type": "observation",
    "source_ids": ["initial"]
  }],
  "limitations": ["Entirely fictional tutorial evidence."]
}
JSON
forecast_packet=$(json_field packet_id < "$forecast_project/packet.json")
vf packet show "$forecast_packet"
vf packet audit "$forecast_packet"

Keep two identifiers: the returned packet_id, saved as forecast_packet, and the finding’s record_id, readiness. Later tasks cite them together as {"packet_id": "…", "record_id": "readiness"}.

The audit may identify missing publication or capture details in this manual fixture. A packet hash verifies content identity; it does not verify that a claim is true. When several reports repeat one original source, record that relationship rather than counting each as independent confirmation.

Use your existing Epiq research instead

Freeze selected cells into the same portable packet format. Replace the database path and author selection.json using the published schema.

Optional / requires an Epiq database
vorhersage schema epiq_selection
vorhersage --project ./my-study epiq freeze \
  --db /path/to/research.sqlite --from selection.json

03 / Start the agent loop

Read the task. Supply the judgment.

  1. PriorLabel the starting judgment or reference class.
  2. DriversDescribe paths to YES and NO.
  3. ResearchCover every domain; explain unknowns.
  4. AssessmentSupply the probability and its reasoning.
  5. ReviewChallenge the estimate in both directions.
  6. IssueFreeze the forecast and set review triggers.
Terminal / start and read the first task
vf run start --from - > "$forecast_project/run.json" <<JSON
{
  "question_id": "factory_east",
  "question_version": 1,
  "forecaster": "agent:tutorial",
  "method": "fictional researched judgment",
  "mode": "simulation",
  "information_as_of": "$(forecast_time)",
  "research_status": "completed",
  "max_searches": 0,
  "max_extra_tasks": 0
}
JSON
forecast_run=$(json_field run_id < "$forecast_project/run.json")
vf next --run "$forecast_run"

Expected: data.disposition is actionable, data.task.kind is prior, and data.revision is 0. next also provides the task’s payload schema, remaining budget, and accumulated context. It does not change state.

We captured the evidence before starting, so research_status: "completed" prevents this starting judgment being labeled a pre-research prior. Simulation runs have a fixed information cutoff; a later evidence update will require a new run.

An agent normally authors a submission envelope containing the task ID, revision, idempotency key, payload, and usage. Define this convenience function once: it fills in the envelope from next, saves each payload for the later revision, and calls submit. It makes no probability judgments.

Terminal / define once for the remaining steps
submit_payload() {
  vf next --run "$forecast_run" > "$forecast_project/next.json"
  python -c '
import json, sys
from pathlib import Path
root = Path(sys.argv[1])
step = json.loads((root / "next.json").read_text())["data"]
payload = json.load(sys.stdin)
(root / (step["task"]["kind"] + ".json")).write_text(json.dumps(payload))
print(json.dumps({
    "task_id": step["task"]["id"],
    "expected_revision": step["revision"],
    "idempotency_key": step["task"]["id"],
    "payload": payload,
    "usage": {"searches": 0, "cost_usd": 0, "model_calls": 0}
}))
' "$forecast_project" | vf submit --run "$forecast_run" --from -
}
Terminal / supply the starting judgment
submit_payload <<'JSON'
{
  "method": "judgment",
  "probability": 0.5,
  "rationale": "An assumed neutral starting point for this fixture.",
  "limitations": ["Not an empirical base rate or a blind prior."],
  "evidence_refs": []
}
JSON

Expected: data.accepted is true and the revision becomes 1. Identical retries are idempotent; changed content under an old key or a stale revision is rejected. Outside this tutorial, reported usage must reflect the agent’s actual work.

04 / Research, assess, and issue

Turn the evidence into a reviewable estimate.

Terminal / map mechanisms and failure paths
submit_payload <<JSON
{
  "drivers": [{
    "name": "Readiness",
    "mechanism": "Dispatch needs a ready production line.",
    "evidence_refs": [{"packet_id": "$forecast_packet", "record_id": "readiness"}]
  }],
  "yes_path": "Preparation finishes and a shipment is dispatched.",
  "no_path": "A remaining dependency blocks dispatch past the deadline.",
  "unknowns": ["Time needed to finish preparation."]
}
JSON

The next four tasks come from the general profile. This short fixture reuses one source to exercise the loop. A real agent should investigate each domain separately and use disposition: "unknown" with an explanation when it cannot assess a domain.

Terminal / complete the four required research tasks
for forecast_domain in base_rates current_state actors_and_process contrary_evidence; do
  submit_payload <<JSON
{
  "disposition": "assessed",
  "interpretation": "The fictional readiness report informs this review; it does not settle the timing.",
  "evidence_refs": [{"packet_id": "$forecast_packet", "record_id": "readiness"}],
  "sources_checked": ["Fictional factory status"],
  "unknowns": ["No additional fixture evidence for $forecast_domain."],
  "conflicts": []
}
JSON
done

The package validates coverage and references. The agent is responsible for substantive research quality. Next, supply a 40% judgment and objections that it could be too high and too low.

Terminal / estimate and challenge the probability
submit_payload <<JSON
{
  "method": "judgment",
  "probability": 0.4,
  "rationale": "Preparation is unfinished; this fixture assigns a substantial chance of delay.",
  "limitations": ["Authored fictional probability; not fitted from data."],
  "evidence_refs": [{"packet_id": "$forecast_packet", "record_id": "readiness"}]
}
JSON
submit_payload <<'JSON'
{
  "decision": "retain",
  "rationale": "Retain the estimate after checking both directions.",
  "objections": [
    {"direction": "too_high", "objection": "Dispatch could fail after preparation.", "response": "The estimate allows substantial failure risk."},
    {"direction": "too_low", "objection": "Preparation might finish quickly.", "response": "Success is plausible but remains uncertain."}
  ],
  "evidence_refs": []
}
JSON

Review can retain the probability, revise it with a rationale, or request bounded additional research. This run has no extra research budget, so we retain the estimate and issue it.

Terminal / freeze the first forecast
submit_payload <<JSON
{
  "stopping_reason": "The available fictional evidence has been reviewed.",
  "review_at": "$forecast_review",
  "triggers": [{"description": "A new report about factory readiness.", "evidence_refs": []}]
}
JSON
forecast_first=$(vf next --run "$forecast_run" | json_field forecast_id)
vf forecast show "$forecast_first"
vf report --question factory_east --format markdown

Expected: the report contains 40% for agent:tutorial. next now says waiting and returns a forecast_id. This completes the forecast, not the event: no outcome has been recorded yet.

The forecast freezes its question version, probability, research coverage, prior timing, evidence references, and input hashes. You can inspect the individual records with forecast show and verify their integrity with doctor.

05 / Update on new evidence

Revise the estimate. Keep the first record.

The original factory example revises East from 40% to 75% after a readiness update. Let’s do the same. Add the new evidence, then register a signal to put the issued forecast in the review queue.

Terminal / record a change and request review
vf research capture --from - > "$forecast_project/update.json" <<JSON
{
  "sources": [{
    "id": "update",
    "url": "urn:vorhersage:fictional:update",
    "title": "Fictional readiness update",
    "excerpt": "The remaining readiness dependency is now complete.",
    "retrieved_at": "$(forecast_time)"
  }],
  "findings": [{
    "id": "ready_now",
    "claim": "The remaining readiness dependency is now complete.",
    "claim_type": "observation",
    "source_ids": ["update"]
  }],
  "limitations": ["Entirely fictional tutorial evidence."]
}
JSON
forecast_update=$(json_field packet_id < "$forecast_project/update.json")
vf signal --from - <<JSON
{
  "question_id": "factory_east",
  "reason": "A fictional readiness dependency was completed.",
  "idempotency_key": "factory-readiness-update",
  "evidence_refs": [{"packet_id": "$forecast_update", "record_id": "ready_now"}]
}
JSON
vf monitor

Expected: monitor lists the first forecast as due because of the signal. It does not update the probability. A revision is another run with the same question version, mode, and forecaster, plus previous_forecast_id.

Terminal / start a linked revision and reuse reviewed payloads
vf run start --from - > "$forecast_project/revision.json" <<JSON
{
  "question_id": "factory_east",
  "question_version": 1,
  "forecaster": "agent:tutorial",
  "method": "fictional researched judgment",
  "mode": "simulation",
  "information_as_of": "$(forecast_time)",
  "research_status": "completed",
  "previous_forecast_id": "$forecast_first",
  "max_searches": 0,
  "max_extra_tasks": 0
}
JSON
forecast_run=$(json_field run_id < "$forecast_project/revision.json")
python - "$forecast_project" "$forecast_update" <<'PYTHON'
import json, sys
from pathlib import Path
root = Path(sys.argv[1])
new_ref = {"packet_id": sys.argv[2], "record_id": "ready_now"}
for kind in ("research", "assessment"):
    path = root / (kind + ".json")
    payload = json.loads(path.read_text())
    payload["evidence_refs"].append(new_ref)
    if kind == "research":
        payload["interpretation"] = "Readiness has improved; dispatch still carries execution risk."
        payload["sources_checked"].append("Fictional readiness update")
        payload["unknowns"] = ["Remaining dispatch risk."]
    else:
        payload["probability"] = 0.75
        payload["rationale"] = "The completed dependency supports a higher fictional estimate."
    path.write_text(json.dumps(payload))
PYTHON
for forecast_task in prior drivers research research research research assessment review issue; do
  submit_payload < "$forecast_project/$forecast_task.json"
done
vf report --question factory_east --format markdown

Expected: the report now lists 40% and 75%. The new forecast links to its predecessor. The small Python block above authors the revised fixture inputs; Vorhersage does not infer the 75% probability from the update. A real agent would reconsider every task, including its objections and unknowns.

Automate future checks with a watch

For a prospective real-event study, configure an Epiq source or research worker and optionally an agent worker. These commands are a template for that separate study; they are not part of the simulation above.

Optional / configure workers before polling
vorhersage schema watch
vorhersage --project ./my-study watch add --from watch.json
vorhersage --project ./my-study watch tick
vorhersage --project ./my-study watch run --interval 30

watch run polls while its process runs; no OS service is installed. Workers receive and return JSON. After the deadline, the work becomes resolution research, not an automatic NO. Polling requires macOS or Linux.

06 / Resolve and score

Check the forecast against the outcome.

Only now do we introduce the fictional outcome. A YES can resolve before the deadline when qualifying evidence establishes that the event already happened. Record when the outcome became known honestly; later forecasts must not enter the ordinary score.

Terminal / add outcome evidence, then resolve
vf research capture --from - > "$forecast_project/outcome.json" <<JSON
{
  "sources": [{
    "id": "shipment",
    "url": "urn:vorhersage:fictional:shipment",
    "title": "Fictional dispatch record",
    "excerpt": "A qualifying shipment occurred before the deadline.",
    "retrieved_at": "$(forecast_time)"
  }],
  "findings": [{
    "id": "shipment_occurred",
    "claim": "A qualifying shipment occurred before the deadline.",
    "claim_type": "observation",
    "source_ids": ["shipment"]
  }],
  "limitations": ["Entirely fictional tutorial evidence."]
}
JSON
forecast_outcome=$(json_field packet_id < "$forecast_project/outcome.json")
vf resolve --from - <<JSON
{
  "question_id": "factory_east",
  "question_version": 1,
  "outcome": "yes",
  "reason": "The fictional dispatch record meets the YES criterion.",
  "known_at": "$(forecast_time)",
  "evidence_refs": [{"packet_id": "$forecast_outcome", "record_id": "shipment_occurred"}],
  "previous_resolution_id": null,
  "idempotency_key": "resolve-factory-east"
}
JSON
Terminal / score the latest eligible forecast
vf evaluate --from - > "$forecast_project/evaluation.json" <<JSON
{
  "question_versions": [{"question_id": "factory_east", "version": 1}],
  "forecasters": ["agent:tutorial"],
  "cutoff": "$(forecast_time)",
  "resolution_as_of": "$(forecast_time)",
  "mode": "simulation"
}
JSON
python - "$forecast_project/evaluation.json" <<'PYTHON'
import json, sys
report = json.load(open(sys.argv[1]))["data"]
print(json.dumps(report["summaries"], indent=2))
PYTHON
vf doctor

Expected: matched_n is 1, matched_brier is 0.0625, and doctor returns ok: true. The evaluator selects the latest eligible forecast: 75%, not the earlier 40%.

Read the score. For a binary outcome, Brier loss is (probability − outcome)², with YES = 1 and NO = 0. Here (0.75 − 1)² = 0.0625. Lower is better. One authored fictional outcome establishes arithmetic, not forecasting skill.

The complete factory example adds a second question and a 50% baseline. Its final agent probabilities are 75% for East (YES) and 30% for West (NO), giving mean Brier loss 0.07625, versus 0.25 for the baseline.

Real comparisons should specify the same question versions, forecasters, mode, and cutoffs. Inspect exclusions for missing forecasts and void, disputed, or unresolved questions. Calibration bins are descriptive; related questions and repeated forecasts are not independent observations.

07 / Compare procedures

Run the same questions through different methods.

The method-comparison example uses the same factory setting. It registers direct judgment and conditional decomposition, then runs two questions × two methods × two repetitions: eight trials. Each question’s evidence is shared across methods.

Terminal / run the eight-trial method example
forecast_methods=$(mktemp -d "${TMPDIR:-/tmp}/vorhersage-methods.XXXXXX")
python examples/method_comparison/walkthrough.py "$forecast_methods"
vorhersage --project "$forecast_methods" method list
vorhersage --project "$forecast_methods" experiment list
python -m json.tool "$forecast_methods/summary.json"
Expected output from the offline method example
MethodAuthored calculationMatched Brier
Direct judgment50% for each question0.25
Conditional decomposition0.80 × 0.75 = 60% for each question0.26

Inspect the saved files: started.json contains eight trial IDs; partial.json records the pause after three worker tasks; completed.json shows all eight forecasts; evaluation.json preserves method scores and the underlying selected forecasts. The fictional scores do not establish a better procedure.

  1. MethodFreeze instructions, task prompts, calculation type, research domains, worker configuration, and budget.
  2. ExperimentPin question versions, method IDs, evidence packets, cutoffs, and repetitions.
  3. RunExecute bounded rounds. Resume with the same experiment ID.
  4. EvaluateAverage repeated Brier losses within question, then compare methods on their common cohort.
Register your own agent methods

This is a template for a separate study. Author the JSON files with the published schemas, use the returned immutable method IDs in the experiment, and replace the uppercase placeholders. experiment run invokes the worker commands you registered; registration and start make no model calls.

Template / use the experiment ID returned by add
vorhersage schema method
vorhersage --project ./my-study method add --from direct.json
vorhersage --project ./my-study method add --from outside-view.json
vorhersage schema experiment
vorhersage --project ./my-study experiment add --from experiment.json
vorhersage --project ./my-study experiment start EXPERIMENT_ID
vorhersage --project ./my-study experiment run EXPERIMENT_ID --max-tasks 20
vorhersage --project ./my-study experiment status EXPERIMENT_ID
# After recording outcomes, supply your resolution snapshot timestamp:
vorhersage --project ./my-study experiment evaluate EXPERIMENT_ID \
  --resolution-as-of RESOLUTION_TIMESTAMP

Changing a registered method requires a new version. Its instructions are supplied to the worker, and submitted prior and assessment types are validated. Each method/repetition has its own forecaster identity, so runs cannot silently replace another arm’s result.

Current scope. Methods use the existing workflow sequence and frozen evidence packets. Workers are trusted subprocesses; external access is not isolated, and usage limits depend on reported counts and costs. Incomplete repetitions can reduce the common scoring cohort.

Optional / Inspect assumptions

See which assumptions move the answer.

A scenario mixture combines mutually exclusive possibilities. The agent defines the scenarios and their probabilities; the tool checks the weights and computes the result. No domain-specific model is required.

Try it / fictional example
Overall success probability52%

0.60 × 0.80 + 0.40 × 0.10 = 0.52

Green: contribution from ready. Gold: contribution from not ready. The remaining space is failure probability.

The complementary scenario always receives the remaining weight. These inputs are illustrative judgments, not measured frequencies. The CLI also calculates sensitivity bounds when ranges are supplied.

Terminal / calculate without issuing a forecast
vorhersage scenario --from examples/workbench_extensions/mixture.json

To use the calculation in a workflow, choose method: "scenario_mixture" for the assessment. Simple judgments, nested conditional paths, and explicit ensembles remain available. Read the assumptions and sensitivity rules →

Reference / Discover the interface

JSON in. Reviewable records out.

Use vorhersage guide, vorhersage schema NAME, and command-level --help to discover the interface. Ordinary output is a JSON envelope; errors go to stderr with a nonzero exit code. --from - accepts stdin.
